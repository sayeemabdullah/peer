# Response to Reviewers

Produces the actual point-by-point letter sent back to the editor and
reviewers. Normally follows `revision-planning.md` — use that sub-skill's
triage table as the backbone of this letter rather than re-deriving the
point list from scratch.

## Structure

For each reviewer point (using the same numbering from the triage, e.g.
R1.1, R1.2):

1. **Quote or closely paraphrase the reviewer's original comment.**
2. **State the response** — accepted, partially accepted, or respectfully
   declined, matching the triage category.
3. **Tie it to a specific change**: what was changed, and exactly where
   ("see Section 3.2, paragraph 2" or "new Table 4" or "we now report the
   95% CI for this effect in the Results, line 214"). A response that says
   "we have addressed this" with no pointer to where is not acceptable —
   reviewers and editors need to find the change without re-reading the
   whole manuscript.
4. **If pushing back**, give the reasoning with evidence — a citation, a
   sensitivity analysis, a direct quote from the manuscript that already
   addresses the concern — not just an assertion that the reviewer is
   mistaken.

## Rules for this letter specifically

- **Never claim a change was made that wasn't made.** If a requested change
  hasn't actually been done yet in the manuscript, either do it first or
  say clearly that it's still pending — don't write the letter as if it's
  already done. This is the single easiest way for a response letter to
  fall apart under a check from the editor.
- **Stay respectful even when pushing back.** No defensiveness, no
  irritation at the reviewer, even if the point was a clear misreading.
  Frame declines around the evidence, not the reviewer's competence.
- **Keep the author's voice.** This is the researcher's letter, not
  Claude's — draft it in the register and tone the user already writes in
  where possible, and treat this as a draft for them to adjust, not a
  finished document to send unreviewed.
- **Address every point**, including minor ones. An unaddressed reviewer
  comment reads as either an oversight or a dodge; if truly not worth a
  substantive change, say so briefly and why.
- **Group by reviewer**, in the order the journal presented them, unless
  the user specifies otherwise — most editors expect this structure.

## Handling declines carefully

When the triage called for "respectfully push back," this letter is where
that gets tested for real — a defensible push-back needs to survive being
read by the reviewer who made the original point and the editor deciding
whether to side with either party. Before finalizing a decline, sanity-check
it: is the evidence actually strong enough to hold up, or does it read as
argumentative? If unsure, flag it to the user rather than defaulting to a
confident tone the evidence doesn't support.
