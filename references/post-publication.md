# Post-Publication

Covers what happens after acceptance: corrections, sharing data and code,
responding to post-publication critique, and handling replication requests.

## Corrections

- If an error is discovered after publication, help the user assess its
  severity honestly first: does it affect the paper's conclusions (needs a
  formal correction/erratum, and in serious cases a retraction) or is it
  cosmetic (may not need formal action, or a lighter-weight fix depending on
  the journal's process)? Don't let the inconvenience or embarrassment of an
  error shrink the assessment of its severity.
- Follow the target journal's actual correction process rather than
  assuming a generic one — publishers vary in what they require (a formal
  letter to the editor, a specific erratum format, in serious cases
  involvement of the institution's research integrity office).
- If the error was caused by an issue this skill would have caught earlier
  (an exclusion applied inconsistently, a mislabeled effect size, a
  transcription error from analysis to manuscript), it's worth naming that
  plainly — not to assign blame, but because it may point to other places
  in the same pipeline worth double-checking.

## Sharing data and code

- If not already done at submission (see `data-management.md`), help
  prepare a well-documented release: clear variable names/codebook,
  a README describing the pipeline from raw data to reported results, and
  fixed dependencies/versions where relevant.
- For data that can't be fully shared (privacy, proprietary, sensitive
  populations), plan for what can be released responsibly — synthetic data,
  code alone, summary statistics, or a documented restricted-access request
  process — rather than defaulting to sharing nothing without explanation.

## Responding to post-publication critique

- Treat a substantive public critique (a comment, a blog post, a failed
  replication, a letter to the editor) with the same honesty-over-defensiveness
  discipline as `receiving-peer-review.md` — evaluate the substance before
  reacting to the fact that it's public and possibly uncomfortable.
- If the critique identifies a real problem, a direct, specific
  acknowledgment (and correction/erratum if warranted) is the credible path;
  minimizing or ignoring a valid critique tends to cost more credibility
  over time than the original error would have.
- If the critique is unfounded or based on a misreading, a calm, evidence-based
  response follows the same rules as `response-to-reviewers.md`: respectful,
  specific, tied to the actual manuscript content, not defensive in tone.

## Replication requests

- Respond to legitimate requests for data, code, or materials needed to
  attempt a replication — this is a normal and expected part of the
  scientific record, not an adversarial act, even when it doesn't feel that
  way in the moment.
- If a replication attempt fails or gets a different result, engage with it
  on the merits: are there genuine differences in method, population, or
  implementation that would explain the discrepancy, or does it point to a
  real problem with the original finding? This connects directly to
  `replication-check.md` and Standing Rule 7 — the honest response to a
  failed replication is rarely a flat denial or a flat concession, and
  the details matter.

## Standing rules this sub-skill enforces directly

Rule 6 (report what didn't work) extends here to failed replications of the
user's own work — these belong in the public record, not quietly omitted
from citation lists or follow-up papers. Rule 10 (honesty over encouragement)
governs how corrections and critiques get handled throughout.
